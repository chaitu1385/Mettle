The one idea

why every design decision below goes the way it does

A conversation is an episode. Each turn is a state, an action, and a reward — but the reward is not observable when the action is taken, and the probability the action was drawn with cannot be recovered afterwards.

So the system is arranged around two facts that are easy to get wrong and impossible to fix later. First: an off-policy estimator needs π_b(a | s) for every action, not just the one that fired — so the full distribution is written to the row at decision time. Second: whether a coaching move worked is only visible in how the person responds to it — so the reward is computed one turn later and written back.

Everything else — the graph, the schema, the CLIs — is plumbing in service of those two.

The graph

langgraph · three nodes, one of which is not a model

The middle node is the point of the whole project. Classification and generation are LLM calls; action selection is ordinary code. The model never picks the move — it is handed one and told to execute it. That is what makes the action a controllable variable rather than a description of whatever the model felt like doing.

The vector that can’t be reconstructed

the reason this milestone exists at all

A rule policy is deterministic: given a state it always picks the same move, so its distribution is one-hot. The epsilon wrapper then spreads exploration mass across the four moves it didn’t pick. Both vectors go in the row — the base one records what the rule wanted, the mixed one is the distribution the sample was actually drawn from.

What the row stores

The row

sqlite · one row per turn, written at three different moments

Provenance is not optional metadata

Mixing prompt versions inside one training set corrupts it silently: the same state maps to different behaviour and nothing downstream can tell. So every row carries prompt_version, and the prompt text is SHA-fingerprinted — a test fails if any prompt string changes without the version being bumped. coach-stats also warns when a dataset spans more than one prompt version or model.

The same reasoning is why server-side refusal fallbacks are deliberately switched off: a silent mid-session switch to a different model would file two models’ behaviour under one model_name.

The reward, and auditing the reward

an unvalidated LLM judge is worse than no reward

The judge is a separate call scoring three dimensions 1–5 — insight, specificity, forward_movement — plus a one-line rationale. It’s a proxy for what you actually care about, and a proxy nobody has checked will look plausible while ranking turns wrongly. Every number built on top of it inherits that error.

So the harness measures the judge against you. Once 40 turns carry a human label, coach-stats reports Spearman correlations per dimension and on the summed score, a judge-band × label confusion table, and the rationale for every outright disagreement — the turns the judge loved and you marked bad, and vice versa. Any correlation below 0.3 raises a warning.

The threshold is signed, not absolute: a judge that reliably anti-correlates with you is the worst case of all, and abs() would hide it.

How the package is layered

imports point downwards only

One rule is enforced by a test rather than by good intentions: each third-party boundary lives in exactly one module. anthropic only in llm.py, langgraph only in graph.py, scipy only in stats.py. The domain never learns who the vendor is — which is also why the whole decision loop runs in tests against a stub, with no network and no API key.

What is still unproven

Not one line of this has talked to the live API — there was no key in the build environment. Three things are therefore unverified: that the structured-output request shape is accepted as written, that Pydantic’s generated schema passes the validator, and — the one that matters — whether the classifier produces a varied distribution of states across real conversation.

If it returns much the same state every turn, the rule policy collapses onto one action and the dataset is worthless for learning anything. No test can detect that. Only transcripts can.

The proof point

Ten turns and one command. Three things tell you it works: ten rows each carrying a full probability vector; epsilon-explored sitting near 20%; and an action distribution that isn’t one action at 90%.

export ANTHROPIC_API_KEY=...
coach-run --seed 7      # ~10 turns, then /quit
coach-stats

If the distribution looks flat, the fix is prompt work in prompts.py plus a PROMPT_VERSION bump — which is exactly the situation that mechanism exists for.

Deliberately out of scope

and what the next milestone is

No learned policy, no off-policy estimators, no web UI, no auth. The reason for logging action_probs now — before any of that exists — is that IPS, SNIPS and doubly-robust estimators can be added later without re-collecting a single turn. That is the entire argument for doing the boring instrumentation first.

The order from here:

  • Run sessions until there are a few hundred turns.
  • Label at least 40 and check the judge actually tracks your labels.
  • Only then fit a policy — and evaluate it off-policy against the logged distributions.
